## 一、I2C 协议基础与 ESP-IDF Legacy API

### 1.1 I2C 帧结构

I2C 是两线制同步串行总线（SDA 数据线 + SCL 时钟线），所有从设备挂在同一条总线上。
一次典型的"写寄存器地址 + 读数据"流程如下：

```
Master → Slave（写阶段，告知要读哪个寄存器）
┌───────┬──────────────┬───┬──────────────┬───┬──────┐
│ START │ 设备地址+W(0) │ACK│  寄存器地址  │ACK│      │
└───────┴──────────────┴───┴──────────────┴───┴      │
                                                       │ Re-START
Master ← Slave（读阶段，从设备送出数据）               │
┌───────┬──────────────┬───┬──────┬─────┬──────┬──────┤
│ START │ 设备地址+R(1) │ACK│ 字节1 │ ACK │ 字节2│ NACK│ STOP
└───────┴──────────────┴───┴──────┴─────┴──────┴──────┘
```

关键规则：
- **ACK**（0）：接收方表示"收到，继续"
- **NACK**（1）：最后一个字节读完后 Master 发 NACK，告诉 Slave 停止
- **Re-START**：不发 STOP，直接再发 START，切换读写方向——这是读操作的标准做法

### 1.2 ESP-IDF Legacy I2C 驱动的命令链写法

ESP-IDF 的 Legacy I2C API（`driver/i2c.h`）使用"命令链（command list）"模式：

```c
// 读单个字节（i2c_esp32_read）
i2c_cmd_handle_t cmd = i2c_cmd_link_create();
i2c_master_start(cmd);                                          // START
i2c_master_write_byte(cmd, (addr << 1) | WRITE, ACK_CHECK_EN); // 设备地址+W
i2c_master_write_byte(cmd, reg_addr, ACK_CHECK_EN);            // 寄存器地址
i2c_master_start(cmd);                                          // Re-START
i2c_master_write_byte(cmd, (addr << 1) | READ, ACK_CHECK_EN);  // 设备地址+R
i2c_master_read_byte(cmd, data, NACK_VAL);                     // 读1字节，发NACK
i2c_master_stop(cmd);                                           // STOP
i2c_master_cmd_begin(i2c_num, cmd, timeout);                    // 执行
i2c_cmd_link_delete(cmd);
```

`i2c_cmd_link_create()` 到 `i2c_cmd_link_delete()` 之间的所有操作只是**构建命令链表**，
不会立即产生 I2C 信号。`i2c_master_cmd_begin()` 才是真正触发硬件执行的那一步，
执行完毕后返回 `ESP_OK` 或错误码。

### 1.3 为什么要在同一事务内读两个字节？

LM75A 温度寄存器（0x00）是 16-bit，必须在**同一个 I2C 事务**里连续读出 MSB 和 LSB。

**如果分两次读会怎样？**

```
// 错误做法：分两次
i2c_esp32_read(addr, 0x00, &msb);   // 事务1：MSB = 22°C
// ← 传感器此刻恰好更新了温度寄存器 → 23°C
i2c_esp32_read(addr, 0x00, &lsb);   // 事务2：LSB 已是 23°C 的 LSB
// 结果：拼出来的温度值既不是 22°C 也不是 23°C，是乱的
```

LM75A 每 100ms 自动更新一次温度寄存器。两次事务之间若更新发生，高低字节将属于不同次的测量，
导致计算结果异常（可能偏差好几度甚至产生符号错误）。

**正确做法：单事务读两字节**

```c
// i2c_esp32_read_word() 的实现
i2c_master_read_byte(cmd, &data[0], ACK_VAL);   // MSB，发 ACK（还有更多字节）
i2c_master_read_byte(cmd, &data[1], NACK_VAL);  // LSB，发 NACK（这是最后一字节）
```

ACK/NACK 的区别：
- 读中间字节 → 发 **ACK**，告诉 Slave "继续输出下一字节"
- 读最后字节 → 发 **NACK**，告诉 Slave "停止，我不需要更多了"

STTS751 温度的 MSB 和 LSB 分别在不同寄存器地址（0x00 和 0x02），只能分两次读，
但其内部寄存器是锁存的，读 MSB 时 LSB 同时被锁住，直到读完 LSB 才解锁，
所以两次读仍然一致。LM75A 没有这个锁存机制，必须用单事务读。

## 二、LM75A 寄存器与温度数据解析

### 2.1 LM75A 寄存器一览

| 地址 | 名称 | 位宽 | 读写 | 说明 |
|------|------|------|------|------|
| 0x00 | Temp | 16-bit | R | 当前温度（11-bit 有效） |
| 0x01 | Conf | 8-bit | R/W | 工作模式配置 |
| 0x02 | Thyst | 16-bit | R/W | 迟滞温度阈值 |
| 0x03 | Tos | 16-bit | R/W | 过温停机阈值 |

**Conf 寄存器（0x01）各位含义：**

```
Bit 7~5: 未使用（读回 0）
Bit 4~3: OS 故障队列（00=1次，01=2次，10=4次，11=6次）
Bit   2: OS 极性（0=低有效，1=高有效）
Bit   1: OS 工作模式（0=比较器，1=中断）
Bit   0: 关断模式（0=正常，1=低功耗关断）
```

写 `0x00` = 正常模式 + 比较器模式 + OS 低有效 + 故障队列 1 次。

**上电默认值就是 0x00**，所以 `lm75a_configure()` 里写 0x00 更多是一种"确认设备在线并初始化"的动作。

### 2.2 温度寄存器格式（11-bit 有符号）

```
Temp 寄存器（16-bit）：
 MSB（Byte 0）                 LSB（Byte 1）
 D7  D6  D5  D4  D3  D2  D1  D0 | D7  D6  D5  D4  D3  D2  D1  D0
 ──────────────────────────────────────────────────────────────────
 T10 T9  T8  T7  T6  T5  T4  T3 | T2  T1  T0   0   0   0   0   0
```

- 有效位是 **D10~D0**（11 位），最高位（T10/MSB.D7）是**符号位**
- LSB 低 5 位固定为 0，不携带信息
- 分辨率：最低有效位（T0 = LSB.D5）= **0.125°C**

**典型值对照：**

| 温度 | MSB | LSB | 16-bit raw（hex） |
|------|-----|-----|------------------|
| +125°C | 0x7D | 0x00 | 0x7D00 |
| +25°C | 0x19 | 0x00 | 0x1900 |
| +22.875°C | 0x16 | 0xE0 | 0x16E0 |
| 0°C | 0x00 | 0x00 | 0x0000 |
| −0.125°C | 0xFF | 0xE0 | 0xFFE0 |
| −25°C | 0xE7 | 0x00 | 0xE700 |
| −55°C | 0xC9 | 0x00 | 0xC900 |

### 2.3 为什么除以 256.0 而不是 2048.0？

数学上有两种等价写法，用哪种取决于如何看待 16-bit raw 值。

**理解方式 A（右移 5 位后除以 8）：**

```
11-bit 值 = raw_16 >> 5       // 去掉低5位的0
温度 = (raw_16 >> 5) * 0.125  // 每个 LSB = 0.125°C
     = (raw_16 >> 5) / 8.0
```

**理解方式 B（直接除以 256，本工程用的方式）：**

```
温度 = raw_16 / 256.0
```

为什么等价？将低5位去掉等于右移5，除以8等于再右移3，合计右移8位，即除以256。

$$\text{temp} = \frac{\text{raw}_{16}}{2^8} = \frac{\text{raw}_{16}}{256}$$

方式 B 代码更简洁，只要把两个字节拼成 `int16_t` 直接除就行：

```c
int16_t raw = (int16_t)((buf[0] << 8) | buf[1]);
float temperature = raw / 256.0f;
```

> ⚠️ 强制转换 `(int16_t)` 必须在拼合之后做，不能先转再拼：
> `buf[0]<<8` 的结果是 `int`（32位），`|buf[1]` 之后仍是 `int`，
> 最后 `(int16_t)` 截断到 16 位，负温度的符号位才能正确传入。

### 2.4 与 STTS751 的差异对比

| 项目 | STTS751 | LM75A |
|------|---------|-------|
| 分辨率 | 12-bit（0.0625°C） | 11-bit（0.125°C） |
| 温度 MSB 寄存器 | 0x00 | 0x00（同） |
| 温度 LSB 寄存器 | **0x02**（分离地址） | **随 MSB 连续读**（同一寄存器块） |
| 配置寄存器 | 0x03 | **0x01** |
| 转换速率寄存器 | **0x04**（需要单独设置） | 无（固定连续转换，约 100ms/次） |
| 厂商/产品 ID | 0xFE/0xFD（可用于验证） | **没有**（无法通过读 ID 确认型号） |
| 读两字节的方式 | 可分两次（内部锁存） | 必须单事务（无锁存） |

## 三、I2C 地址扫描与总线卡死问题

### 3.1 I2C 7-bit 地址与地址引脚

LM75A 的 7-bit 地址格式：

```
Bit 6  5  4  3  2  1  0
     1  0  0  1  A2 A1 A0
```

固定前缀 `0b1001`，后 3 位由 A2/A1/A0 引脚决定，总计 8 种地址（0x48~0x4F）。

| A2 | A1 | A0 | 地址 |
|----|----|----|------|
| GND | GND | GND | **0x48** |
| GND | GND | VCC | 0x49 |
| GND | VCC | GND | 0x4A |
| GND | VCC | VCC | 0x4B |
| VCC | GND | GND | 0x4C |
| ... | ... | ... | ... |

> **悬空引脚的危害**：地址引脚悬空时，其电平由总线上的弱上拉和周边漏电决定，
> 是不确定的。引脚上有轻微电磁干扰时可能随机跳变，导致地址不稳定。
> 设计时必须将所有地址引脚明确接到 VCC 或 GND。

### 3.2 NACK 与总线卡死（Bus Stuck）

**正常 NACK（无设备应答）：**
当 Master 发送地址字节后，总线上没有任何设备响应，SDA 保持高电平（NACK），
Master 感知后放弃并发 STOP，总线释放，一切正常。

**总线卡死（SDA stuck low）：**
某些异常情况（如 Master 复位发生在 Slave 正在发送数据的中途）会导致 Slave 把 SDA 拉低，
等待 Master 继续发 SCL，而 Master 已经复位不知情，总线就永久卡死（SDA = 0）。

ESP-IDF Legacy I2C 驱动在某些 NACK 情况下不会完整清理总线，
**连续扫描多个不存在的地址**时，NACK 产生的错误状态可能叠加，
导致后续对真实设备的访问也失败。

**解决方法：**
1. **把最可能存在的地址放在扫描列表第一位**（避免无效 NACK 积累）
2. 或在每次失败后调用 `i2c_reset_tx_fifo()` / `i2c_reset_rx_fifo()` 清理硬件状态
3. 或在失败后短暂延时再重试

本工程采用方法 1：`{0x48, 0x49, 0x4A, 0x4B}`，0x48 在第一位。

### 3.3 为什么主应用扫描失败而测试程序成功？

这是调试过程中出现的一个有趣问题：

| | 测试程序 | 主应用 |
|---|---------|--------|
| 访问方式 | 直接用 `0x48` | 扫描数组 `{0x49, 0x48, ...}` |
| 结果 | ✅ 成功 | ❌ 0x49 NACK → 0x48 也失败 |

根本原因：主应用的扫描数组当时以 `0x49` 开头（A0=VCC 的参考设计默认值），
对 0x49 产生 NACK，总线状态未完全恢复，紧接着扫描 0x48 也失败了。
测试程序跳过了扫描，直接用 `0x48`，从未触发 NACK，所以没有问题。

## 四、SX1302 HAL 的 RSSI 温度补偿机制

### 4.1 为什么 LoRa 网关需要温度补偿？

SX1302 内部射频前端（LNA、混频器等）的增益会随温度变化，
导致测量到的 RSSI 值在不同温度下存在系统性偏差。
厂商通过实测标定，得到一个 RSSI 误差与温度的关系多项式，
在软件里实时修正，使 RSSI 值更准确。

### 4.2 补偿公式与 cn490 系数

HAL 层的完整补偿是一个 4 次多项式，但对于 cn490 频段只使用了二次和一次项：

$$\text{offset} = \frac{c_a T^4 + c_b T^3 + c_c T^2 + c_d T + c_e}{65536}$$

cn490 参考设计系数（来自 `global_conf.cn490.json`）：

| 系数 | 值 |
|------|-----|
| $c_a$ | 0 |
| $c_b$ | 0 |
| $c_c$ | 20.41 |
| $c_d$ | 2162.56 |
| $c_e$ | 0 |

**22.9°C 时的计算验证：**

$$\text{offset} = \frac{20.41 \times 22.9^2 + 2162.56 \times 22.9}{65536} = \frac{10705.7 + 49523.6}{65536} \approx 0.918 \text{ dB}$$

这与串口日志完全吻合：`RSSI temperature offset applied: 0.918 dB (current temperature 22.9 C)`

最终 RSSI 计算为：`rssi_corrected = rssi_raw + offset`

### 4.3 调用时机：在收包之后而非之前

一个关键问题：温度读取（I2C 操作）是否会影响 LoRa 收包？

查看 `loragw_hal.c` 中的 `lgw_receive()` 调用顺序：

```c
int lgw_receive(uint8_t max_pkt, struct lgw_pkt_rx_s *pkt_data) {
    // 1. 先从 SX1302 FIFO 里取出所有已收到的包
    nb_pkt_fetched = sx1302_fetch(lgw_context, ...);

    // 2. 对每个包做 RSSI 温度补偿
    //    ← 此时 LoRa 包已经安全存在内存里了
    for (i = 0; i < nb_pkt_fetched; i++) {
        lgw_get_temperature(&current_temperature);
        // ... 用 current_temperature 计算 offset 并修正 rssi
    }
    return nb_pkt_fetched;
}
```

`sx1302_fetch()` 把数据从 SX1302 片上 FIFO 读到 ESP32 内存，之后 SX1302 可以继续
独立接收新的 LoRa 包，不受后续 I2C 操作的影响。所以 I2C 通信**不会造成丢包**，
CRC 失败率上升是纯粹的硬件问题（电源噪声 → 射频噪底抬高）。

## 五、硬件噪声与 RF 干扰

### 5.1 去耦电容的作用

数字芯片（包括 I2C 传感器）在 SCL 每次上升沿时会短暂向 VCC 汲取电流脉冲。
如果 VCC 线上没有靠近芯片的储能元件，这个电流脉冲会在 VCC 走线的寄生电感上
产生电压尖刺（$V = L \cdot \frac{di}{dt}$），形成高频噪声。

**100nF 陶瓷电容的作用：**
- 存储电荷，在瞬态电流需求时补充，抑制 VCC 上的电压跌落
- 谐振频率约 50~200MHz（取决于实际 ESL），正好覆盖数字噪声频率段
- **必须紧靠芯片 VCC 和 GND 引脚放置**，走线长了等效电感增大，效果大打折扣

```
          VCC
           │
          ─┤ 100nF    ← 这里的电容越靠近 LM75A VCC 引脚越好
           │
    ┌──────┘
    │ LM75A
    │ VCC pin
    └──────
           │
          GND
```

### 5.2 I2C 总线电气特性对 RF 的影响

I2C 总线是**开漏**结构，靠上拉电阻（通常 4.7kΩ）拉高。SCL 的典型波形：

```
VCC  ─────┐    ┌────┐    ┌─────
          │    │    │    │
GND  ─────┘    └────┘    └─────
     ← 上升慢（RC）  下降快（驱动器）
```

上升沿的斜率由 `R_pullup × C_bus` 决定（典型 100kHz 时约 1μs），
对 RF 的直接干扰很小（频率太低）。

**真正的干扰来源是传感器 VCC 上的开关噪声**，通过以下路径传播：
1. LM75A VCC 噪声 → PCB 电源平面 → SX1302 VCC → 射频前端
2. LM75A VCC 噪声 → 辐射 → SX1302 天线输入

防护措施优先级：
1. ✅ 100nF 去耦电容（最关键，首先解决）
2. ✅ I2C 连线短于 10cm，远离 RF 走线和天线
3. ✅ LM75A 的 GND 引脚通过短粗走线接到主地平面
4. ⬜ 如果仍有问题，可在 LM75A VCC 串入 10Ω 电阻 + 100nF 再旁路，形成 RC 滤波
